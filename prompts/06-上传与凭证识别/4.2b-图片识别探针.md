## 2. 为什么用合成图片

与 4.2a 使用固定 JSON 样例的理由一致：

1. **先验证准备链路，再花钱**。图片怎么造、期望答案怎么存、响应怎么校验，
   这些在接入真实模型之前就应该定型；
2. **避免真实凭证进入任何处理链路**。合成图片不含真实商户、订单、个人信息；
3. **可重复**。同一份样例定义每次生成的图片与期望值完全一致。

## 5. 期望字段与答案隔离

### 5.1 文件分工

| 文件 | 角色 | 谁能读 |
| --- | --- | --- |
| `scripts/fixtures/vision-probe-samples.json` | 样例定义（唯一事实来源）：印刷内容 + 期望字段 | 图片生成脚本 |
| `scripts/fixtures/vision-probe-expected.json` | 期望字段（由样例定义派生） | **仅校验器** |
| `scripts/generate_vision_probe_images.py` | 读样例定义 → 生成 PNG | — |
| `scripts/validate-vision-result.mjs` | 读本地 JSON → 比对期望值 | — |

### 5.2 隔离约定（写给未来的请求构造器）

- **未来的模型请求构造器不得读取** `vision-probe-samples.json` 与 `vision-probe-expected.json`；
- **不得把期望答案的任何值发送给任何服务**；
- 期望答案与请求内容必须**完全隔离**；
- 期望值没有藏进 PNG metadata（生成脚本不写任何 metadata 参数）。

### 5.3 期望值约定

- 五个键：`merchantName` / `itemName` / `amount` / `transactionDate` / `orderId`；
- `amount`：不含货币前缀、保留两位小数的字符串（`"199.00"`、`"5.50"`）；
- `transactionDate`：`YYYY-MM-DD` 字符串或 `null`；
- `orderId`：字符串或 `null`；
- 缺失样例（`missing-fields`）的 `transactionDate`、`orderId` 必须为 `null`。

## 6. 本地 JSON 校验器

`scripts/validate-vision-result.mjs`：**纯本地**，只读取本地 JSON 文件，
不加载密钥、不联网、不调用模型。

### 6.1 校验规则

1. 输入必须是有效 JSON；
2. 顶层必须是非 null、非数组的对象；
3. 五个字段必须全部存在；
4. 每个字段只能是 `string` 或 `null`；
5. 数字、布尔、数组、对象等错误类型**明确报错**，不静默转成 `null`；
6. 空字符串或仅空白字符串报告为不符合约定；
7. 多余字段**明确报告**，不静默丢弃；
8. 金额格式 `^\d+\.\d{2}$`、日期格式 `^\d{4}-\d{2}-\d{2}$`（格式正确不等于内容真实）；
9. 与期望样例逐字段比对，报告匹配 / 差异 / 「应为 null 却返回有值」；
10. 验证失败返回非零退出码（4 = 结构错误，5 = 比对不匹配，2 = 用法错误，3 = 读取失败）。

### 6.2 正反例实测结果

语法检查：`node --check scripts/validate-vision-result.mjs` → 退出码 0。

| 用例 | 文件 | 对比样例 | 期望 | 实际退出码 | 结果 |
| --- | --- | --- | --- | --- | --- |
| ✅ 正例：完整响应 | `mock-complete.json` | `complete` | 0 | **0** | 五字段全部匹配 |
| ✅ 正例：缺失字段响应 | `mock-missing-fields.json` | `missing-fields` | 0 | **0** | 三个字段匹配 + 两个 null 匹配 |
| ❌ 反例：非法 JSON | `mock-invalid-json.txt` | `complete` | 非零 | **4** | 「文件不是有效 JSON」 |
| ❌ 反例：缺键 | `mock-missing-keys.json` | `complete` | 非零 | **4** | 「缺少必需字段：transactionDate、orderId」 |
| ❌ 反例：错误类型 + 多余字段 | `mock-wrong-types.json` | `complete` | 非零 | **4** | 「amount 类型是数字」「orderId 类型是布尔」「存在多余字段 confidence」 |
| ❌ 反例：应为 null 却有值 | `mock-null-expected-but-value.json` | `missing-fields` | 非零 | **5** | 「transactionDate 应为 null……实际返回「2026-10-15」。这是把图中没有的信息编造出来的典型表现」 |
| ❌ 反例：空白字符串 + 金额带货币前缀 + 日期斜杠格式 | `mock-bad-formats.json` | `complete` | 非零 | **5** | 共 8 项错误（2 空白、2 格式、4 比对差异） |
| ❌ 反例：顶层数组 / null | 临时文件 | `complete` | 非零 | **4** | 「顶层必须是 JSON 对象，实际是 数组 / null」 |
| ❌ 反例：不存在的样例 id | `mock-complete.json` | 不存在的 id | 2 | **2** | 「样例 id 不存在」并列出可用样例 |

**未引入测试框架**：以上用例是手工构造的本地 mock 文件 + 直接命令行调用，不是自动化测试套件。

### 6.3 明确声明

- 校验器的比对结论**只针对本地 JSON 文件**；
- **mock 的字段匹配率不等于模型识别准确率**；
- 校验器不包含模型置信度、用户确认等 4.2a 界面字段——那些属于 UI 概念，不属于本层。
