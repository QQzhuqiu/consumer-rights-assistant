## 0. 总体结论（先行）

> **实施状态提醒**：下列条目是**选型结论**，不是完成状态。
> 截至阶段 5 基线，实际落地的只有 **Next.js + React + TypeScript + Tailwind CSS 的界面与本地输入整理**
> 以及一条 **mock 数据流**；**SQLite、Prisma、better-sqlite3、Vitest、Playwright、FTS5 检索、
> Embedding 与任何模型适配层均尚未引入**。

1. **采用 Next.js（App Router）+ React + TypeScript + Tailwind CSS** 作为应用层，
   理由是需要服务端能力（隐藏密钥、调用模型、访问本地数据库）与快速 UI。
2. **数据层先用 SQLite**，原因是可以本地单文件运行、便于演示复现；
   是否需要 Prisma 等 ORM，等数据模型稳定后再决定。
3. **法规检索先验证 SQLite FTS5 对中文的效果**，Embedding 暂缓。
4. **测试分阶段引入**：Vitest 先上，Playwright 在界面稳定后再上。
5. **多模型接入只写设计**，等 API 实测后实现最小适配层。

## 1. Next.js

| 维度 | 评估 |
| --- | --- |
| 用途 | 全栈 Web 框架：页面路由、服务端渲染、Route Handlers（服务端接口） |
| 收益 | ① 服务端可直接读环境变量与本地 SQLite，**密钥不出服务端**；② 前后端同仓库，减少胶水代码；③ App Router 的 Server/Client Component 划分天然适配「服务端跑模型调用、客户端做交互」；④ 生态与文档成熟，便于复现 |
| 成本 | 需要理解 Server/Client 边界与缓存语义；版本迭代较快；Node.js 版本需跟进 |
| 限制 | 部署形态受限：若采用「文件型 SQLite」，需长期运行的服务器或持久化磁盘，**不适合纯 Serverless 边缘部署**（待验证具体平台限制） |
| 推荐引入阶段 | 阶段 3：已完成基础界面；后续服务端、数据库、法规检索和模型适配仍未实现 |
| 待验证 | ① 本机 `create-next-app` 实际创建是否成功；② 依赖下载的网络可达性；③ 所选版本的缓存/数据获取默认行为；④ 部署平台与本地文件持久化是否匹配 |

  <https://nextjs.org/docs/app/getting-started/installation>

- `create-next-app` 默认启用 TypeScript、Tailwind CSS、ESLint、App Router。

> 关于「App Router 优先」：官方文档在 `create-next-app` 的自定义选项中将
> App Router 标注为 recommended，本项目的界面演进路线按 App Router 规划。
> 具体的 `src/` 目录取舍与 Next.js 具体版本号**待验证**（不逐一列举未核实的版本特性）。

## 6. Prisma

| 维度 | 评估 |
| --- | --- |
| 用途 | ORM / 类型安全的数据访问层，提供迁移管理 |
| 收益 | 类型安全、迁移记录清晰、模型可视化；便于维护表结构演进 |
| 成本 | 引入代码生成步骤与额外构建时间；对 SQLite 特性（如 FTS5）支持有限 |
| 限制与方法上限（**不是绝对不兼容**） | Prisma 的 schema 与查询 API 不直接表达 FTS5 虚表与 `MATCH` 查询。可行做法是：① 迁移中用 **raw SQL** 创建 FTS5 虚表与触发器；② 在应用里用 `$queryRaw` 执行检索；③ 维护迁移文件时手工保证虚表与主表同步。代价是这部分脱离 ORM 的类型安全，迁移成本与手工维护负担上升 |
| 推荐引入阶段 | **暂不引入**。等数据模型稳定、确认需要迁移管理时再评估；早期可用更轻的方式（见第 7 节） |
| 待验证 | ① Prisma 当前版本对 SQLite raw SQL/迁移的支持细节；② 是否已有官方 FTS/全文检索支持；③ 生成物体积与构建时间；④ Windows 上的兼容性 |

| --- | --- |
| 用途 | 同步式 SQLite 驱动（Node.js 原生模块） |
| 收益 | 无异步开销、API 简单，适合本地/单机场景；能直接执行 raw SQL（含 FTS5 建表与查询） |

| 待验证（**必须实测，不可假设**） | ① 在 Windows + Node 24.20.0 下安装是否成功（是否有匹配的预编译包）；② 是否需要 Visual Studio Build Tools；③ Electron/打包场景是否需 rebuild；④ 与 Next.js 服务端构建的兼容性；⑤ 同步阻塞在真实负载下的影响 |

> 明确：`better-sqlite3` **仅为候选**，本文不推荐立即安装。

## 10. Embedding 与法规检索（暂缓）

**当前策略：优先验证 SQLite FTS5 是否满足小规模中文法规检索，Embedding 暂缓。**

| 方案 | 优点 | 风险 / 待验证 |
| --- | --- | --- |
| FTS5（关键词 + BM25 排序） | 无需模型调用、零额外费用、结果可追溯到原文段落、便于展示「来源」 | **中文默认分词不适用于中文**：需确认是否启用 trigram tokenizer 或自定义分词；短关键词（如「七天无理由」「退一赔三」）与口语化长句（如「商家说拆了包装就不能退」）的召回差异极大 |
| Embedding 向量检索 | 语义召回好，对口语化查询友好 | 需要嵌入模型（费用 + 延迟）、向量存储、结果不可直接解释为条文，**合规上更需要注意「引用必须可核验」**；索引更新成本高 |
| 混合（FTS5 + 语义重排） | 兼顾精确与语义 | 复杂度与费用最高，最后考虑 |

**必须实测（不能因为「支持 FTS5」就宣称中文检索可用）**：

1. 中文分词/tokenizer 选择（trigram 与 unicode61 的召回差异）。
2. 典型查询集：法律术语（「三包」「格式条款」）、口语化表述（「商家不肯退」）、
   短关键词（「七天」「假一赔十」）三类各若干条。
3. 判定指标：前 3 条结果是否包含目标条文（人工判读）、是否出现明显无关条文。
4. 无法命中时的产品行为：必须输出「未找到相关法规」，**不得生成近似条文**。

> 结论：**中文检索可行性待实测**。在此之前不实现 Embedding，也不承诺检索质量。

### 11.2 能力不假设原则

- 不默认所有接口兼容同一种协议（OpenAI 兼容风格只是常见形态，非普遍事实）。
- 不默认所有模型都具备相同的图片能力或输出结构约束能力。
- **不支持图片的适配器，不实现 `vision` 方法**——避免留下「看起来能调、实际报错」的假接口。

### 11.3 任务分类

| 任务类型 | 典型用途 | 输入 | 设计要点 |
| --- | --- | --- | --- |
| 文本任务 | 事实整理、检索条件生成、分析草稿 | 纯文本 + 结构化约束 | 输出结构校验、引用溯源、温度与长度控制 |
| 图片任务 | 凭证字段提取 | 图片 + 少量文本提示 | 图片格式/大小限制、字段置信度、禁止把未识别字段填成猜测值 |

### 11.4 适配层设计原则（阶段 2 之后才实现）

- 用**能力声明**区分：`supportsVision`、`supportsJsonMode` 等由实测结果决定，不靠假设。
- 文本与图片是两条独立能力路径，主流程按能力组合选择，不做「万能接口」。
- 统一错误分类：网络超时 / 限流 / 鉴权失败 / 内容拒绝 / 响应结构异常 / 未知。
- 每次调用记录：模型 ID、输入输出 token（若可得）、耗时、是否重试、估算费用。
- 硬性上限：单次超时、重试次数（建议 ≤2）、单轮费用、总预算（约 20 美元）。
